# Decisions

Choices made where `SPEC.md`, `RULES.md` or `PLAN.md` were ambiguous or inconsistent.
Newest at the bottom of each section. "Phase N" says when the decision takes effect.

## Applied (Phases 0-1)

- **Git:** the project directory was not a repository; `git init -b main` was run in Phase 0 so
  per-phase commits are possible.
- **Single version source:** `__version__` in `src/ghostrules/__init__.py`, read by hatch.
- **Rule registry:** `rules/registry.py` holds `Rule` + `@rule`; `rules/__init__.py` re-exports it
  and imports the rule modules. `Rule.scans_decoded` marks GR010-GR016.
- **Hidden-text pass:** text decoded by a rule (`Finding.decoded`) is scanned as a virtual
  `instructions` target by `scans_decoded` rules only (no recursion). Results are attributed to
  the parent's location and get +1 severity (cap critical).
- **Suppression scope:** inline `ghostrules-ignore` never suppresses GR001/GR002 (SPEC §6), and
  also cannot suppress findings derived from decoded hidden text. `ScanResult.suppressed` counts
  suppressed findings so reports can show it.
- **Size/binary limits:** the 2 MB / binary skip only applies to unrecognised files added by
  `--all-files`. Known target files are always scanned, otherwise padding a file would hide it.
- **Symlinks:** never followed during repo discovery (no escaping the root, no loops). `--home`
  accepts symlinked dotfiles.
- **Explicit file argument:** `scan some/file` scans it even if it is not a known target
  (`kind = other`, unless its name matches a target glob).
- **Reported paths:** relative to the scan root; with several roots, prefixed by the root as given;
  home files are labelled `~/...`.
- **Columns:** 1-based, in Unicode code points (not UTF-16). SARIF must declare
  `columnKind: unicodeCodePoints` (Phase 5).
- **Decoding:** files are read as UTF-8 with `surrogateescape`; reporters must sanitise lone
  surrogates before printing (Phase 5).
- **Rule crashes:** recorded in `ScanResult.errors` and treated as a failed scan by the CLI
  (exit 2) rather than silently dropped.
- **Config unknown keys:** an unknown key in `.ghostrules.toml` is an error (catches typos).
- **Config from the scanned repo:** honoured as the spec says, but `ScanResult.config_source` is
  kept so the summary can show that a repo-supplied config (which could disable rules or add
  `allow_domains`) was loaded.
- **JSONC:** comment/trailing-comma stripping is string-aware and preserves offsets and lines.

## Applied (Phase 2)

- **Pattern tables pulled forward:** GR005 must know whether a comment "matches any GR010-GR016
  pattern", so `rules/patterns.py` (regex tables, `match_injection`, `find_encoded_payloads`) was
  written in Phase 2. Phase 3 builds the rules on top of it and refines the tables.
- **GR001 flag exception:** only a real subdivision flag (`🏴` + tags spelling `[a-z]{2}[a-z0-9]{1,3}`
  + cancel tag) is ignored. A looser check would let a payload hide behind a flag.
- **GR002/GR003 grouping:** one finding per line (first to last offending character) rather than
  per character. GR001/GR004 are one finding per contiguous run, as specified.
- **GR002 "substantial RTL":** at least 10 Hebrew/Arabic-family letters and at least 30% of all
  letters in the file.
- **GR003 exceptions:** a ZWJ/ZWNJ is only ignored when it is isolated (not part of a run) and
  has a legitimate neighbour: emoji on both sides for ZWJ, or an Arabic/Indic letter on either
  side for ZWJ/ZWNJ. A leading BOM (offset 0) is ignored.
  Severity is high if the line has >= 5 or the file has >= 20 flagged characters.
- **GR004 base exemption dropped:** RULES.md exempts runs "directly following an emoji / CJK base"
  but also sets a threshold of 3. Legitimate use is one selector after one base, so with a
  threshold of 3 the exemption has nothing to exempt, and emoji is the very carrier used by the
  known technique. Runs of >= 3 are always reported.
- **GR005:** comments inside fenced code blocks are ignored (they are visible when rendered);
  an unterminated `<!--` counts as a comment to the end of the file (GitHub hides the rest);
  a GR015 match requires the base64/hex to decode to printable text. GR005 applies to
  `instructions` files and to `other` files with a Markdown extension, never to `config`.
- **GR006:** plain words are checked in `instructions` files only; URLs are checked in every
  kind. Words need Latin letters plus a known lookalike (hand-written table of Cyrillic/Greek
  confusables, defined by code point); URL host labels mixing Latin with *any* Cyrillic/Greek
  letter are flagged. Findings inside a URL are high, plain words low.
- **Columns:** `end_column` is exclusive; multi-line matches are clamped to the end of the first
  line.
- **Fixtures:** generated into `tests/fixtures/unicode/<case>/` by `scripts/make_fixtures.py`,
  committed for reviewability, and regenerated by a session fixture before tests run. The script
  and the tests write invisible and non-Latin characters as escapes only.

## Applied (Phase 3)

- **Matching:** each rule matches the raw text and a whitespace-normalised copy of the whole
  file (`ScanTarget.normalized`, with an offset map back to the original), then drops overlapping
  duplicates. Gaps in GR012 patterns are bounded (200 chars) so the normalised pass cannot join
  distant lines.
- **Scope:** GR010-GR016 apply to `instructions` only (RULES.md: "content of instruction files")
  and have `scans_decoded=True`, so hidden text from GR001/GR004/GR015 is re-scanned by all of
  them (GR015 included, which catches double encoding).
- **GR012 severity:** always critical. The "high elsewhere" case in RULES.md is realised by
  GR105/GR107 (Phase 4), which reuse these patterns for MCP commands and hooks.
- **`allow_domains`:** the scanner hands the list to rules through `ScanTarget.allow_domains`
  (read-only input, rules stay pure). GR012 and GR013 skip a match when every URL in it is on an
  allowed domain; GR013 also skips an allowed collector domain.
- **GR013:** exfiltration forms are critical; a collector domain alone is high, and critical when
  on the same line as an exfiltration instruction. A collector domain inside an already
  reported instruction is not reported again. Known false-positive risk (as specified): "include
  the token ... https://..." fires; use `allow_domains` or an inline ignore.
- **GR014:** `.env` must not be preceded by a word character (so `process.env` is fine) nor be
  `.env.example/.sample/.template/.dist`. A verb negated within three words before it ("never
  print", "do not send") is ignored. For `copy`/`paste`, a path after "to/into/as" is a
  destination, not something read ("Copy .env.example to .env.local").
- **GR015:** high when the run decodes to printable text (shown in `decoded`); medium for opaque
  runs only if they look like random bytes (entropy >= 4.5 bits/char, mixed case and digits, not
  inside a path/URL) and hex runs that are not sha384/sha512 digest lengths. Fenced blocks are
  skipped unless labelled with a shell language; unlabelled blocks count as non-shell.
- **GR010 in code blocks:** low, message "appears inside a code block"; no other rule downgrades.
- **Excerpts:** messages quote the matched text (whitespace collapsed, 80 chars). Secret masking
  of snippets/messages is still to do centrally in Phase 4.

## Applied (Phase 4)

- **Masking (`secrets.py`):** a secret of >= 20 characters is shown as first 4 + `****…` + last 4
  (`ghp_****…a1b2`, the CLAUDE.md format; RULES.md's wording differs only by the ellipsis);
  shorter ones as `****`. `mask_secrets` covers known token formats, bearer tokens, URL
  passwords, and `key=value` / `--flag value` pairs whose name looks secret and whose value looks
  like one (>= 16 chars, entropy >= 3.5, no spaces, not a placeholder/URL/path). It is idempotent.
- **Single choke point:** `Finding.__post_init__` masks `title`, `message`, `snippet`, `decoded`
  and `fix_hint`, so any finding, from any rule, is safe to print, serialise or repr. On top of
  that `build_finding` masks the *line* before cutting the snippet (positions are remapped), so a
  context window can never leave a readable fragment of a secret. Scanner warnings and rule-crash
  errors are masked too.
- **Masking is broader than detection:** a secret glued to letters (`xghp_...`) is still masked
  even though GR101 requires a word boundary to *report* one; the ambiguous `sk-` prefix needs a
  digit and some entropy in that case so words like `task-management-...` are left alone.
- **Reporter guarantee:** reporters do not exist yet. They can only print what `Finding` and
  `ScanResult` hold, which is already masked; `tests/test_secret_masking.py` additionally runs
  every module of `ghostrules.reporters` exposing `render(result) -> str` against a scenario
  with every secret format in every place (Phase 5 reporters must expose that function).
- **Mutation check:** with masking switched off the dedicated tests fail (7 of 9), so they do
  detect a leak.
- **Test secrets:** defanged fakes in `tests/secret_samples.py` with the real shapes; the GitHub
  one is `ghp_` + 36 chars (`EXAMPLE` x5 + `0`), since the spec's 32-char sample cannot match
  GR101.
- **`ServerDef`:** carries `spans` (character offsets of the server key and of each command, arg,
  env value, header value and URL) instead of the single `line` in PLAN §4, so findings point at
  the exact value. Shapes read: `mcpServers`, `servers`, `mcp.servers`, `projects.*.mcpServers`
  (`~/.claude.json`) and Codex `[mcp_servers.*]` (TOML locations are found by text search inside
  the server's table, so they are approximate when the same value repeats).
- **GR101 scope:** known formats are checked in every value of a server (env, args, headers, URL
  incl. query and password) and in the settings `env`; the generic rule needs a secret-looking
  key name (env/header name, `--flag=value`, or the flag before the value, URL parameter).
- **GR102:** knows npx, bunx, `pnpm dlx`, `yarn dlx`, uvx, `pipx run` (value-taking flags
  skipped, `-p/--package/--from/--spec` read as the package). Pinned = exact `x.y.z` (npm) or
  `==`/`@version` (Python) or a git commit SHA; local paths and archive URLs are not judged.
  `pkg@1`, `@latest`, ranges and branch/tag refs are unpinned.
- **GR103:** `http://` only (not `ws://`); `${VAR}` hosts are skipped; loopback = `localhost`,
  127.0.0.0/8, `::1`.
- **GR104:** "filesystem-like" = `filesystem` in the name/package, or a `fs`/`files` token
  (so `pdfsearch` is not one). The package argument itself is never counted as a path.
- **GR105:** also matches `dash/ksh/fish`, combined flags like `-lc`, and PowerShell
  `-enc/-EncodedCommand`; critical when the command string matches a GR012 pattern (which
  includes encoded PowerShell).
- **GR106:** one finding per dangerous option, pointing at that argument.
- **GR107:** besides the specified keys, hook commands are also checked for shell-style
  exfiltration (`curl ... .env`, `cat ~/.ssh/id_rsa | curl`, `env | curl`) and collector domains,
  since GR013's prose patterns would miss them. Gemini `yolo` is read only under `.gemini/`.
- **GR108:** `enableAllProjectMcpServers: true`, plus Gemini-style `"trust": true` on a server
  as the "equivalent auto-trust flag".

## Applied (Phase 5)

- **Default command:** `ghostrules`, `ghostrules .` and `ghostrules --format json` all run `scan`
  (a custom Typer group prepends it unless the first argument is a command or `--help`).
- **Precedence:** CLI flag > config file > default. `--disable` is added to the config's list.
  Config is looked up in the first scan path (or its directory).
- **`--fail-on` scope:** only findings left after `--min-severity` and after inline suppressions
  count, so a hidden finding can never fail the build (and the notes line shows suppressions).
- **Exit codes:** 2 also when the scan itself failed (missing path, crashed rule), even if
  nothing was found, so a broken scan can never look clean. The table then says "Scan
  incomplete" instead of showing a green tick.
- **Output channels:** the table (and its notes, warnings and errors) goes to stdout. For
  `json`/`sarif`/`markdown`, stdout carries only the report and diagnostics go to stderr, so
  `ghostrules scan --format json | jq` always works. `-o FILE` writes the report (table: plain
  text, no colour) and prints "report written to FILE" on stderr.
- **Reporters** each expose `render(result, **options) -> str`; `reporters/common.py` holds the
  shared helpers (it has no `render`, so it is not treated as a reporter).
  Lone surrogates from undecodable input bytes are replaced before output, so nothing can crash
  on encoding, and stdout is switched to UTF-8 when the terminal's code page is not.
- **Table:** findings grouped by file; files ordered by worst severity, then those hiding
  decoded text, then path. Severity badges are colour-coded pills; invisible-character tokens
  are highlighted; the decoded hidden text sits in a red panel titled "Decoded hidden text"
  (no colon: it is a panel title, not a line) with matching malicious phrases and URLs
  highlighted. A finding derived from hidden text already shown above is rendered compactly
  (`↳ ...`) instead of repeating the panel. Snippets stay on one line (ellipsis). Width is
  capped at 120 columns.
- **Ordering of `result.findings`:** severity, then findings that carry decoded hidden text,
  then path/line/column/rule, so every format leads with the hidden instruction.
- **Notes shown to the reader:** configuration loaded from the scanned repo and the number of
  findings hidden by `ghostrules-ignore`, because both can hide findings (see Phase 1).
- **SARIF:** validated in tests against the official 2.1.0 schema (vendored in `tests/data/`,
  checked with `jsonschema`, now a dev dependency). `columnKind` is `unicodeCodePoints`.
  `helpUri` points to `PROJECT_URL#<rule id>`; **`PROJECT_URL` in `ghostrules/__init__.py` still
  has the placeholder `OWNER` and must be set before publishing.** Findings in `--home` files
  are left out and mentioned in the run's notifications.
- **JSON:** the specified keys plus `warnings`, `errors` and, in `summary`, `suppressed`,
  `files_with_findings` and `config_source`.
- **Markdown:** truncated at 100 rows; every cell is escaped (`|`, backticks, `<`, `>`) so
  scanned content cannot inject Markdown or HTML into a PR comment.
- **`reveal`:** numbered listing; tag characters and variation selectors are tokens without
  names (long runs), other invisible characters have names; HTML comments are highlighted;
  decoded ASCII (tags) and bytes (variation selectors) follow each line. Output is masked.
- **`clean`:** removes exactly what GR001-GR004 flag (see Phase 2 exceptions), except
  bidirectional controls in substantially right-to-left files, which are kept and reported.
  A leading BOM goes unless `--keep-bom`. It refuses to overwrite an existing
  `FILE.ghostrules.bak`. Line endings and undecodable bytes are preserved. The dry-run diff
  shows removed characters as tokens and is masked.
- **Demo repositories:** `scripts/make_demo.py` generates `examples/poisoned-repo` (minimal for
  now; Phase 6 completes it so every rule fires) and `examples/clean-repo`; a test checks that
  the checked-in files equal the generator's output.

## Applied (Phase 6)

- **Poisoned demo covers every rule** (RULES.md acceptance criterion), not only the list in
  PLAN §6; a test fails if a newly added rule is not triggered by it. Extra cases beyond the
  plan: `.github/copilot-instructions.md` (variation-selector bytes, base64 payload, Cyrillic
  homoglyphs in a word and a URL, `--dangerously-skip-permissions`), a filesystem server on `/`,
  a `bash -c "curl ... | bash"` server, and `~/.ssh/id_rsa` in the skill. All payloads are
  defanged and generated by `scripts/make_demo.py` from escapes.
- **Hero first, in every format:** findings (and, in the table, files) are ordered by
  severity, then those carrying decoded hidden text, then files nearer the repository root, then
  path. Without the depth rule a nested `.github/...` file sorted before `AGENTS.md` and the
  JSON/SARIF/Markdown reports led with the wrong finding.
- **The GIF:** `demo/demo.tape` (vhs): `cat` the innocent-looking `AGENTS.md`, then
  `scan ... | head -24` (the first 24 lines are exactly the hidden-text block and its derived
  findings; colours are kept with `FORCE_COLOR=1`), then `reveal`. A test estimates the length
  from the tape (typing time plus sleeps, about 12.6 s) and checks the 24-line cut does not split
  the panel. **The GIF itself is not committed**: vhs, ffmpeg and ttyd were not available where
  this was built; run `vhs demo/demo.tape` from the repository root.
- **`.gitattributes`:** `examples/**` and `tests/fixtures/**` are `-text`, everything else LF, so
  Windows checkouts (autocrlf) keep these byte-exact files intact; the "examples are up to date"
  test would otherwise fail on the Windows CI runner.

## Applied (Phase 7)

- **Action inputs never reach a shell by text substitution.** Every `${{ ... }}` goes through an
  `env:` variable, and a test fails if any workflow or action script contains `${{` in a `run:`.
  The action installs itself from `$GITHUB_ACTION_PATH` (the same directory as
  `${{ github.action_path }}`), with Python 3.12.
- **Job flow (SPEC §7):** the scan step runs with the requested `fail-on`, writes
  `ghostrules.sarif` and only *records* the exit code (output `exit-code`); the SARIF upload and
  the Markdown job summary follow; the last step fails the job with the recorded code and an
  `::error` annotation (1 = findings, anything else = the scan could not run). A test executes
  these exact scripts with bash against the demo repositories.
- **SARIF upload cannot fail the job** (`continue-on-error`): it is unavailable on forks and on
  private repositories without code scanning, and the scan result must stay the only gate.
- **`path` should stay `.`:** SARIF locations are relative to the scanned path, and GitHub resolves
  them from the repository root. Documented in the input description and the README.
- **pre-commit hook:** `entry: ghostrules scan`, `pass_filenames: false`, no `always_run`
  (pre-commit then runs it only on commits that stage at least one file, which is every real
  commit). It scans the repository root, exits 1 on findings.
- **Workflows:** `ci.yml` also smoke-tests the demos (clean exits 0, poisoned exits 1) on every
  OS. `self-test.yml` runs the local action on the poisoned demo with `fail-on: none` and asserts
  the SARIF has results led by GR001, then with the default `fail-on` and asserts the step fails
  with exit code 1, then on the clean demo and asserts an empty SARIF. All three workflows pass
  `actionlint` (run locally from a throwaway virtualenv; it is not a project dependency).
- **Release (`release.yml`, on `v*` tags):** build once, then publish to PyPI through
  *Trusted Publishing* (OIDC, environment `pypi`, no token or secret anywhere; a test checks), then
  create the GitHub release with the built files. The build job refuses to continue if the tag
  differs from `__version__` or if `CHANGELOG.md` has no non-empty `## [X.Y.Z]` section
  (`scripts/changelog_section.py`), so **Phase 9 must turn `[Unreleased]` into `[0.1.0]`** before
  tagging. One-time setup on PyPI: add a pending publisher for the repository, workflow
  `release.yml`, environment `pypi`.
- **Placeholders to fill before publishing:** `OWNER` in the README snippets and in
  `PROJECT_URL` (see Phase 5).

## Applied (Phase 8)

- **README** follows PLAN §8 in order (name, tagline, badges, GIF, why, install, quick start,
  Action, pre-commit, rules table, supported files, configuration, roadmap, contributing,
  security, license, author), plus a short "Limits" section: a heuristic scanner should say
  that no findings is not a proof. A test checks the section order.
- **Absolute links and images.** PyPI renders the README without the repository around it, so
  relative links and images would be broken there. Links to repository files use
  `https://github.com/BardLaudian/ghostrules/blob/main/...`; a test checks every such target exists.
  The GIF is referenced by its `raw.githubusercontent.com` URL and is not committed (see Phase 6).
- **Rules table** is generated from the registry by `scripts/gen_rules_table.py` between
  `rules-table` markers (`--write` / `--check`); a test fails when it drifts. Each ID cell has an
  `<a id="gr001">` anchor so the SARIF `helpUri` (`PROJECT_URL#gr001`) lands on the rule. Pipes
  in descriptions are escaped. "Severity" is the typical one (`Rule.severity`); escalation
  conditions live in `docs/RULES.md`.
- **Also under test:** every scanned file pattern and `--home` path appears in the README, every
  `scan` option is documented, every rule is in `docs/RULES.md` and vice versa, the issue forms
  are valid and the "Why" section links its five primary sources. The sources were opened and
  checked when written: Rehberger (ASCII Smuggler, 2024-01-14), Butler (emoji smuggling,
  2025-02-08), Boucher & Anderson (Trojan Source), Pillar Security (Rules File Backdoor,
  2025-03-18) and Invariant Labs (MCP tool poisoning, 2025-04-01).
- **SECURITY.md** uses GitHub private vulnerability reporting and publishes no e-mail address; it
  lists what counts as a vulnerability (executing or fetching scanned content, an unmasked
  secret, crafted input that breaks the scan or injects into a report, a way to suppress GR001/GR002)
  and what is an ordinary bug (false positives and negatives).
- **Issue forms:** "New rule proposal" and "False positive", both opening with a reminder to use
  defanged examples only; blank issues are disabled and the security link is offered instead.

## Applied (Phase 9: final review)

- **Self-scan:** `ghostrules scan .` and `ghostrules scan . --all-files` are clean, using a
  `.ghostrules.toml` that excludes the deliberately poisoned `examples/**` and `tests/fixtures/**`
  (and build/cache directories). A test and two CI steps keep it that way.
- **Two real defects found by the review and fixed:**
  GR005 treated a documented `` `<!--` `` in inline code as an unterminated comment hiding the
  rest of the file (a false positive on this repository's own docs; inline code is now skipped
  like fenced blocks, while a lone backtick or a comment after a code span still counts), and the
  table squeezed the finding title into a few characters when the path was long (the location now
  moves to its own line when the row does not fit).
- **Windows paths:** discovery already worked on POSIX-style relative paths; path matching now
  also accepts backslashes (in paths and in `exclude` / `extra_targets` patterns). No test assumes
  a separator, symlinks and bash-only tests are skipped on Windows, and files compared byte for
  byte are protected by `.gitattributes`. The Windows runner in CI is the first real run.
- **Verified here:** the full suite (654 tests, 98 % line coverage) on Python 3.10, 3.12 and 3.13;
  on 3.10 with the minimum declared dependency versions (`typer` 0.12, `rich` 13, `click` < 8.2);
  `ruff`, `ruff format --check` and `mypy`; `python -m build` plus `twine check` on both artifacts;
  the wheel installed in an empty virtualenv scanning the demos; every report format on the
  poisoned demo (28 findings in JSON, SARIF and Markdown, SARIF schema-valid, no unmasked token);
  `actionlint` on the workflows. **Not verifiable here:** a real GitHub Actions run, the
  Windows and macOS runners, PyPI publishing, and recording the GIF.
- **`scripts/set_owner.py GITHUB-NAME`** replaces the `BardLaudian/ghostrules` placeholder in the README,
  SECURITY.md, CONTRIBUTING.md, `PROJECT_URL`, the issue-form link and the PyPI project URLs in
  one go (dry run available, idempotent, refuses invalid names).
- **Release notes:** `CHANGELOG.md` now has `## [0.1.0] - 2026-10-27`, which `release.yml`
  requires; a test checks it against `__version__`.
- **Tag:** `v0.1.0` is created locally on the final commit and not pushed.

## v0.1.1 — GR012 context-aware severity

- **Registered severity stays `critical`:** it is the maximum the rule can report; the actual
  severity comes from the table in RULES.md.
- **`trust_known_installers = false`** makes every non-allow-listed match critical (0.1.0
  behaviour), not just the known installers.
- **Row order:** the risky-URL row (http, IP, port, collector) comes before `allow_domains`, as in
  the table, so an allow-listed domain served over plain `http://` is still critical.
- **URL scope:** `bash <(curl URL)` and `eval "$(curl URL)"` have the URL after the matched
  text, so those matches are judged on the rest of the line.
- **Inline code span:** `ScanTarget.code_span_at` wraps the existing CommonMark-style span finder.

## v0.2 Phase 0 — agent models and prior art (checked 2026-10-28)

### Agent models re-checked against the official docs
Details and quotes are in `docs/AGENT_MODELS.md` (changes marked `[0-28]`). Pages were read
through a summarising fetch tool, so re-read a page before relying on a detail that sets a severity.

- **claude-code:** the draft was right on load order, AGENTS.md precedence, imports and HTML-comment
  stripping. New: invalid rule frontmatter loads the rule unconditionally; per-file truncation limit
  for on-demand files (40,000 chars on 200K windows); AGENTS.md needs v2.1.277+; external
  symlinked rules load only without `paths` after approval; `claudeMdExcludes` can remove files
  (documented limitation, not modelled).
- **claude-code, external imports are relative to the working directory, not the repo root.** SPEC
  and RULES define GR020 against the repository root. They agree when `--cwd` is the repo root
  (the default). Decision: GR020 is evaluated against `--cwd` for claude-code and against the repo
  root for copilot-cli ("must stay inside the repository"); the message says which.
- **claude-code, depth:** official docs say four hops (guides quoting five are wrong). The docs do
  not say whether a direct import is hop 0 or 1: modelled as hop 1, with chains of exactly 4–5
  hops marked `(unverified)`.
- **claude-code, HTML comments:** documented only for CLAUDE.md files. AGENTS.md read via the
  setting, rules and imported files are modelled as "seen" so GR005 never downgrades on a guess.
  This narrows the headline claim of the agent-aware GR005: it is exact for CLAUDE.md,
  CLAUDE.local.md and .claude/CLAUDE.md.
- **copilot-cli:** unchanged and re-confirmed. Still UNVERIFIED: import base path, depth limit,
  code-span handling, `excludeAgent` effect in the CLI.
- **cursor:** the draft was a guess; now verified. Rule types match. Differences: `.cursor/rules`
  rules must be `.mdc` (plain `.md` is ignored), `@file` in rules is **not** an import (so the Cursor
  model has no import edges), AGENTS.md is supported at root and nested. `.cursorrules` is not on the
  page: kept as `always`, `(unverified)`. User and Team Rules live outside the repo: documented
  limitation.
- **generic (agents.md):** only "nearest file wins" is documented; reading ancestors is not. The
  nearest is verified, the others `always (unverified)` so a security scan does not miss them.

### Prior art: does anything already resolve `@` imports for security scanning?
Searched (web, 2026-10-28) for scanners that follow `@path` imports, compute an agent's effective

## v0.2 Phase 1 — Markdown primitives

New: `markdown_utils.py` (`strip_html_comments`, `parse_frontmatter`, `strip_frontmatter`,
`Stripped` with a line map back to the original file) and `imports.py` (`find_imports`). No rule or
scan behaviour changes yet. Inline code spans already existed from 0.1.1.

- **Import start (UNVERIFIED approximation).** Claude Code documents what is skipped, not the exact
  token grammar. `find_imports` calls an import *certain* when `@` starts a line or follows
  whitespace (so `user@example.com` and `git@github.com` never match) and *loose* when it follows
  `( [ { < , ; : > = | *` (markdown links, emphasis). Loose ones are returned with
  `certain=False`; Phase 2 should scan them but label them `(unverified)`, so a guess about the
  grammar cannot hide a payload.
- **Trailing punctuation** (`. , ; : ! ? ) ] } > *` and quotes) is not part of the path, except a
  balanced `)` (`@docs/a(1).md`). Also unverified; the cost of being wrong is a missing file (GR022).
- **`@mentions` and npm scopes** are returned like any token. `Import.looks_like_path` (has `/` or
  `\`, starts with `.` or `~`, or ends in an extension) is what Phase 3 uses to decide whether a
  token that resolves to nothing is worth a GR022. `@README` has none of those and is still a real
  import when the file exists; resolution decides.
- **Quoted paths** are not imports (documented). `find_imports(include_quoted=True)` returns them
  with `quoted=True` for GR022.
- **Imports inside block-level HTML comments** are returned with `in_comment=True`. The docs do not
  say whether Claude Code expands imports before or after stripping comments, so the context
  engine should follow them but mark them unverified.
- **HTML comment stripping** models a CommonMark type-2 HTML block: the comment starts a line
  (up to three spaces of indent) and ends at the line holding `-->`. Text after `-->` stays. Not
  stripped, on purpose: comments in fenced code (documented), mid-paragraph or in a list item or
  blockquote (the docs only say "block-level"), and comments that never close. Anything not stripped
  counts as *seen*, which is the safe direction for GR005 and the lock.
- **Front matter** supports `key: value`, flow lists, block lists, quoted strings and `true/false`;
  numbers stay strings. Anything else sets `unparsed` with the reasons. A plain value starting with
  `*`, `&`, `!`, `|`, `>`, `{`, `[`, `%`, `@` or a backtick, or containing `: `, is flagged because a
  strict YAML parser rejects it; that matters because the docs say Claude Code then loads a rule
  as if it had no `paths` (an unquoted `paths: **/*.ts` silently becomes an always-on rule). The raw
  value is kept in `data`. Cursor's parser may be more lenient than the one in Claude Code; consumers
  should treat `unparsed` as "behaviour differs per agent".
- **Line numbers.** `Stripped.line_map` gives the original line of every kept line, and
  `removed` records what was cut (kind, original lines, text), which Phase 5 needs for "changed, not
  visible to <agent>".

## v0.2 Phase 2 — context engine

New: `globs.py` and the `agents/` package (`repo`, `base`, `claude_code`, `copilot_cli`, `cursor`,
`generic`). Nothing is wired into `scan` yet.

- **Entries vs edges.** `ContextGraph.entries` is the ordered list of files the agent loads, each
  imported file placed right after its importer; `edges` records every `@` occurrence (status
  `loaded`, `duplicate`, `missing`, `directory`, `quoted`, `external`, `blocked`, `symlink`,
  `too_large`, `depth`, `cycle`) in file order, so GR020/GR022/GR023 can be derived without
  re-parsing. A file reached twice is one entry plus a `duplicate` edge; its `via` is the first chain.
- **Unreadable entries.** An import that leaves the tree (`/abs`, `~/x`, `../out`) becomes an entry
  with `readable=False` and no text (never read). Claude Code keeps the importer's load state and
  the note "requires approval"; Copilot CLI marks it `blocked`. Symlinks, over-4-MiB files and
  AGENTS.md files the agent skips are `blocked` entries too, so `context` can show them with the reason.
- **Hop counting.** Refined from Phase 0: hops 1-4 load, hop 5 is loaded and `(unverified)`, hop 6+ is
  not loaded (see AGENT_MODELS). Copilot: limit 4, every imported entry unverified (base path, depth
  and code-span rules are undocumented).
- **External = outside the working directory** for Claude Code (a file inside the repo but outside
  `--cwd` is readable and carries the approval note); **outside the repository** for Copilot, where it
  is blocked. User-scope files (`~/...`) never show the approval note.
- **Imports inside rules** (`.claude/rules/*.md`) are followed for Claude Code and marked like other
  imports: the docs only describe imports in CLAUDE.md/AGENTS.md. Ancestor-directory rules (between
  the repo root and `--cwd`) are not documented either: assumed `always`, unverified.
- **CLAUDE.md symlinks.** ghostrules does not read them (even `CLAUDE.md -> AGENTS.md`, a documented
  pattern), so the entry is `blocked` and the symlink still counts as "a CLAUDE.md exists" for the
  AGENTS.md rule. `context` will therefore under-report such a repo; GR025 will say why.
- **Unparseable rule front matter** (Claude Code): the rule is `always`, unverified, with the whole
  file as text. Cursor is lenient: the front matter data is used and removed, unverified.
- **Copilot `*.instructions.md` without `applyTo`** are `manual` (unverified): the docs say
  path-specific files apply only when `applyTo` matches. `applyTo` is matched against the target
  path relative to the repository root.
- **Cursor:** `.md` files in `.cursor/rules` are `blocked` ("ignored"), `.cursorrules` is `always`
  unverified, nested `AGENTS.md` below the working directory is `on_demand`, and no imports exist.
- **Generic:** the nearest `AGENTS.md` to the target (or the working directory) is verified, the
  ones above it on the path are `always` unverified, the rest `on_demand`.
- **Globs.** One matcher for every agent: anchored, `*` stays in a segment, `**/` spans directories,
  braces expand up to 1,000 patterns (then stay literal), bad `[` makes one pattern invalid, dotfiles
  match, case-sensitive by default. Cursor and Copilot have their own matchers in reality; this
  approximation is the same for all and is the main source of `matches` being wrong in edge cases.
- **Not modelled:** managed policy files, `claudeMdExcludes`, `--add-dir`, `COPILOT_CUSTOM_INSTRUCTIONS_DIRS`,
  `/instructions`, directories above the repo root; each is listed in `ContextGraph.notes` or
  AGENT_MODELS.

## v0.2 Phase 3 — scan integration and import rules

- **What becomes a scan target.** For every scan root the models of the configured agents (default
  all four) are run with the session at the root. Every readable file in those contexts is scanned
  as `instructions`: imported files, and also files the 0.1 globs did not know (`.claude/rules/**`).
  A file an agent loads by itself is "standalone" and gets no `via`; only a file that imports alone
  reach gets `via`, `agents` and the tag. `exclude` applies to these files too. `--no-follow-imports`
  drops the imported files but keeps GR020-GR023, which only read the importing line.
- **`agents` in findings** is filled only when the file was reached through an import. 0.1 JSON/SARIF
  output (and a 0.1 test that pins the exact key set) stays byte-for-byte the same for everything
  else, and `via`/`agents`/`tags` are omitted from JSON when empty.
- **GR024 is registered** (so `ghostrules rules`, the README table and SARIF list it) but is a tag, not
  a detector: its check never runs. Putting it in `disable` is equivalent to `--no-follow-imports`.
- **Graph rules** (`scope="graph"`) receive a `ScanContext` (every agent's graph plus the loaded
  targets). Findings are placed on the importing line, so the importer's own `ghostrules-ignore`
  markers apply to GR020-GR023 and nothing else; a marker never reaches the imported file. GR025 has
  no line to suppress and reports on the link's own path.
- **GR020** uses each agent's own definition of "outside" (Claude Code: outside the working
  directory, which at scan time is the root; Copilot CLI: outside the repository), so it is
  info for user-level files and never reads the target.
- **GR021** looks at the path as written. The context engine itself never reads a sensitive file: an
  in-repo `@.env` becomes an unreadable `sensitive` entry, so the file is not hashed or scanned either.
  High instead of critical when the import is uncertain (inside an HTML comment or after punctuation).
- **GR022** skips `@mention`-like tokens (no `/`, no extension, no leading `.`/`~`), missing targets of
  uncertain imports, and anything outside the tree (that is GR020). The "cut at an unescaped space"
  hint is computed by the engine when a missing path becomes an existing one with the next words
  appended (at most four).
- **GR005** gets `AgentView`s on the `ScanTarget`: the comment line ranges each agent strips. Default
  config models all four agents, and Copilot CLI sees CLAUDE.md comments, so the severity only
  drops to info for teams that set `agents = ["claude-code"]`. Files no model covers behave as in 0.1.
- **Edited 0.1 test.** `test_every_rule_fires_somewhere_in_the_poisoned_repo` now checks the 0.1 rules
  (`id < GR020`): the poisoned demo stays frozen at 7 files / 28 findings (other 0.1 tests pin that)
  and has no imports or symlinks. `examples/import-chain-repo` (Phase 6) will carry the same check for
  GR020-GR025. Nothing else in the 0.1 suite changed.

## v0.2 Phase 4 — `ghostrules context`

- **Demo repo created early.** `examples/import-chain-repo` (generated by `scripts/make_demo.py`,
  checked for staleness like the other two) exists now so the tree can be shown; Phase 6 adds the
  `lock` scenario and the tapes. It has the SPEC §7 chain, a `.env` import (GR021, the file holds a
  fake value and is never read), an import outside the repository (GR020), a conditional rule, an
  on-demand `src/legacy/CLAUDE.md` and an `AGENTS.md` that Claude Code skips. Imports resolve
  relative to the importing file, so `docs/setup.md` writes `@../.env`.
- **`--agent all` = one tree per agent**, not a merged tree: what loads, when, and how a file is
  transformed differ per agent, and a merged tree would hide that. (The SPEC's "union, each entry
  tagged with its agents" is what `scan` findings carry in `agents`; `lock` will use per-agent lists.)
  `all` means the agents of the config (`agents = [...]`), all four by default.
- **Root and paths.** `--root` defaults to the enclosing git root, else the current directory, so
  inside `examples/` the git root is the ghostrules repo itself: use `--root` for the demos (or
  make them their own repo). `TARGET` and `--cwd` are read relative to the current directory and
  to the root; of the readings inside the root, the one that exists wins. Symlinks are not resolved.
- **What is scanned.** The whole root is scanned with the config of the root and the shown agents,
  and findings are kept for files that appear in a displayed context. The rest are only counted
  ("+N findings in files these agents do not load"). Files in `exclude` still appear in the tree but
  are not scanned, as in `scan`.
- **Tree.** Imported files hang under their importer in the order the imports are written.
  Imports that do not load are leaves where they were written (`✕ missing`, `↺ cycle`, `✕ too deep`...)
  except mention-like tokens (`@alice`). Findings from one hidden text (GR001 and what it decodes
  to) are shown as one block with the decoded text, like the `scan` table. `(unverified)` marks
  everything the docs leave open, which makes the Copilot CLI tree noisy on purpose.
- **`--show-text`** prints the text each agent receives, once per distinct text, with invisible
  characters revealed (the `reveal` view); Markdown wraps it in `<details>`.
- **Exit codes** as `scan`: 1 when a finding in the displayed context reaches `--fail-on`
  (default `high`), 2 on bad arguments or a failed scan, 0 otherwise. `--no-scan` never fails.

## v0.2 Phase 5 — `ghostrules lock`

- **Where the old text comes from.** The lock must show *which lines are new* (with invisible
  characters revealed, which a pull-request diff cannot do) but must not keep the text. Each entry
  therefore stores `lines`: one 64-bit hash per line of the seen text, space separated on a single
  JSON line. A check aligns those with the current lines (`difflib`) and prints the lines that are
  new, with their number in the original file (comment stripping is mapped back); removed lines
  are only counted ("1 line removed (was line 3 of the locked text)"). Alternatives rejected:
  storing the text (bloats and duplicates the repo), asking git for the old blob (needs history
  and a ref, shells out). Cost: about 17 bytes per line; files over 5,000 lines have no `lines`
  and are reported as "too large to compare line by line". The file-level hashes, not the line
  hashes, decide whether something changed: a line-hash collision could only hide a line from the
  display, never a change.
- **`via` in the lock is a list of paths**, not `path:line`. Adding a line above an import would
  otherwise change the identity of every file below it. The check prints the current lines.
- **What is recorded.** For each agent of the config: every entry of the context at the root
  (session start, conditional and on-demand files, imports), including entries ghostrules does not
  read (symlinks, external or sensitive imports, files the agent skips), with `null` hashes. That way
  "AGENTS.md was skipped and now loads" and "an import of `.env` appeared" are changes. Files in
  `exclude` are left out; user-level files (`--home`) are not in the lock. `conditions` is the
  `paths`/`globs` text. Notes, `unverified` and reasons are not stored, so improving a model's
  wording never invalidates a lock.
- **Comparison.** Per agent and per `(path, via)`: added, removed, changed (seen text, load state or
  condition differ) or hidden (the file differs but the text the agent receives does not, e.g. a
  comment Claude Code strips). Agents affected in the same way are merged into one row; if some
  agents see a change and others do not, the file appears in both sections. A lock made for other
  agents than the configuration models is itself a change. A different `generator` is only noted.
- **Exit codes** as specified: 0 up to date, 1 changed, 2 error (missing, corrupt or unsupported lock,
  `--check` with `--update`, bad arguments). Plain `lock` and `--update` overwrite the file and
  print what changed relative to the old one.
- **Scope.** No `--cwd`/`--home`: the lock is repository-wide at the root. It does not run the
  rules; `scan` and `context` do. The README (Phase 7) must say it is a visibility control and
  recommend CODEOWNERS on the lock and on instruction files, since a pull request can update it too.

## v0.2.1

### F1 — symlinks inside the repository are aliases
Source: `docs/v0.2.1/FIXES.md`. 0.2.0 marked `CLAUDE.md -> AGENTS.md` as skipped in `context` and
emitted a GR025 `medium` per link, which claimed Claude reads nothing in the most common real setup.

- **Policy** (also in `docs/AGENT_MODELS.md`): a link ending at a regular file inside the root is an
  alias read under the link's name; chains up to 8 hops, every hop inside the root, no cycles;
  directory links inside the root make the files under them aliases. `Repo.resolve` follows links by
  hand, one component at a time, and decides *before* anything is opened; `Repo.read` and `size` go
  through it, so no code path can open a file outside the root.
- **Only one level of directory-link expansion in `Repo.files`.** A file under a link to a directory
  is listed under the link's name, computed from the real files of the walk. Links inside the target
  directory are not expanded again, which keeps a link to an ancestor from growing the listing.
- **No double counting.** The `AGENTS.md` that a loaded `CLAUDE.md` link points at is a blocked entry
  ("already read through CLAUDE.md (symlink)") in every instructions mode, including
  `claude-md-and-agents-md` (Claude would read the same text twice; reading it once is what matters
  for a scan). The same goes for a file imported under two names: the second one is a `duplicate`.
- **Scan.** Entries are keyed by their resolved path, so the content is scanned once, under the real
  file. Findings in a file an agent reads through a link get `via: ["CLAUDE.md (symlink)"]` and
  `agents`; they do not get the `reached-via-import` tag, because nothing was imported. Findings
  elsewhere keep their 0.1 shape. `via` items without a line number are ignored by the SARIF
  `relatedLocations` builder, as before.
- **Lock.** An alias entry carries `link` (the resolved target) next to the hashes of the target's
  content. The key is omitted when there is no link, so locks without links are byte-identical to
  0.2.0, and `lock_version` stays 1: a 0.2.0 lock read by 0.2.1 differs only where the code now
  resolves a link. Retargeting a link to a file with the same text is reported as a change of
  `symlink target`.
- **GR025.** The registry severity is `high` (the worst case, as for GR012); findings are `high`
  outside the root, `low` for broken, cyclic or too-long links, `info` for the text checkout. An
  alias produces nothing.
- **Windows text checkout.** Any readable entry (not reached by an import, not an alias) whose
  whole text is one line naming an existing file inside the root, relative to its own directory, is
  reported as `info`. Targets starting with `@` or `#`, or leaving the root, are ignored. It reads
  the repository only through `Repo.is_file`.
- **0.2 tests changed on purpose** (they asserted "symlinks are never followed"):
  `test_agents_claude.py` (4 tests), `test_agents_repo.py` (1), `test_lock.py` (1) and
  `test_scan_imports.py` (3) now describe the alias behaviour; the outside-the-root cases they
  covered are kept. `README.md`'s rules table is regenerated.

### F2 — GR022 only for intended file references
- `Import.looks_like_path` is now "has an extension, or starts with `./`, `../`, `~/`, `/`" (it used
  to be true for any `/`). The context engine widens it to a path whose **first segment exists next
  to the importing file** (`ImportEdge.looks_like_path`), checked before the npm-scope look: a real
  `docs/` directory is evidence of intent even though `@docs/missing` has the shape of a scope.
- The spec's "skip tokens matching the npm scope pattern" is therefore implied by the new default
  rather than a separate regex; a scope with an extension (`@types/node.d.ts`) is still reported
  when missing, as the spec says. The same flag drives the `context` tree, so those tokens no longer
  show as a missing leaf either (one definition of "meant as an import").
- 0.2 test changed: `@types/node` is no longer reported (`test_scan_imports.py`,
  `test_imports.py`).

### F4 — GR012 on data pipes and Claude's installer
- Patterns, not post-filters: `| sh`/`bash` no longer matches when followed by `-c`; `| python`
  matches only when nothing but an optional `-` follows before the end of the clause (end of line,
  `|`, `;`, `&`, `)` or a comment). `python3 -u script.py` and `python -c` are data.
- `node -e` and `jq` were never matched; tests now pin that. `| node` without `-e` is still not
  matched (not asked for; no corpus case).
- GR105/GR107 (MCP commands and hooks) share the pattern list, so they stop matching the same data
  pipes. That is the intent of the fix, not a separate change.
- `claude.ai/install.sh` added with its source. The list keeps its existing order (appended, not
  re-sorted) to keep `ghostrules rules --installers` output stable; the spec's "keep sorted" is
  applied to future additions from the corpus run.
